CHECKPOINT: CP-08.1 — Bilingual, button-driven Telegram UX
STATUS: APPROVED — 2026-07-28

## 1. Objective

Make the sell-first Telegram MVP usable by ordinary Uzbek-market residents and staff without
memorizing command syntax: expose Uzbek and Russian, use simple menus/context buttons for routine
staff work, retain commands as a support fallback, and add no paid service or new runtime.

## 2. Scope completed

- Uzbek and Russian are the two visible resident language choices; stored Uzbek Cyrillic sessions
  remain compatible.
- Resident intake, categories, quality replies and notifications support Russian.
- Staff operation results, status labels, report text, help, menus and prompts support Uzbek/Russian.
- `/start` and `/menu` open a persistent staff keyboard for requests, assigned work, overdue work,
  complaints, reports, PDCA, failed notifications, language and help.
- Queue results produce contextual entity buttons. Request, order, complaint, PDCA and notification
  actions execute through callbacks with backend authorization unchanged.
- Text is requested only for required factual input: triage scores, reasons, notes, summaries and
  deadlines.
- Assignment provides executor buttons and a simple Tashkent deadline prompt.
- BEFORE/AFTER evidence buttons arm the next photo without requiring a caption command.
- Quality inspection uses an explicit PASS/FAIL checklist and refuses submission until every item
  is selected.
- Guided state is bounded and expires in memory; no Redis, workflow product, paid localization
  provider or extra process was added.
- Resident intake now collects a validated full name, declared `CRITICAL`/`IMPORTANT`/`PLANNED`
  urgency, and either “as soon as possible” or an exact one-hour preferred visit window.
- Visit selection uses compact day and day-part buttons before showing six hourly choices; all
  displayed dates use Tashkent `DD.MM.YYYY HH:mm`.
- The resident-selected urgency is evidence, not the final operational priority. Authorized staff
  still validate priority through the deterministic triage model.
- Request entity buttons expose an area-authorized bilingual detail view with the resident data
  needed to contact and perform the service.
- `/start` and `/menu` now open a persistent bilingual resident menu for a new request, status,
  language and help. Submission also returns a one-tap status button bound to the generated ticket.
- The address step presents real Telegram location and manual-entry controls. Selecting manual
  entry cannot accidentally persist the control label as an address.
- Photos arriving together are debounced per resident: each Telegram update is processed for
  idempotency, while the resident receives one final album count and one Done button.
- Public `/myid` returns only the sender's Telegram ID. Area-scoped administrators can use a
  bilingual `👥 Staff` flow to grant only operator/executor roles, list managed staff, suspend with
  a reason, and restore access.
- Executor onboarding creates a profile and all active pilot category capabilities. Staff access
  changes are transactional and audited; suspension does not disable the resident identity.

## 3. Persistence and migration

- Migration `20260727221400_modern_sunfire.sql` adds Russian category/checklist labels and expands
  resident/session language constraints with `ru`.
- Existing rows are backfilled by stable category/checklist codes before new columns become
  `NOT NULL`; unknown configured rows retain their Uzbek Latin label as a safe migration fallback.
- Seed is idempotent and supplies Russian values for all pilot categories/checklist items.
- No request, order, audit, evidence, notification, complaint, report or PDCA fact is deleted.
- Migration `20260728045325_pale_terrax.sql` adds the optional legacy-safe profile name, declared
  urgency, preferred visit window, ASAP marker, and the expanded resumable intake steps.
- Migration `20260728061617_conscious_payback.sql` adds managed staff profiles, stable `STF` codes,
  and active/suspended access state. Existing roles and users remain unchanged until explicitly
  provisioned.

## 4. Security and cost review

- Buttons call the same application services and permission checks as command fallback; callback
  visibility grants no authority.
- Callback payloads contain bounded generated reference codes, not resident text, phone, address,
  Telegram IDs, tokens or evidence identifiers.
- Guided text/photo/checklist state expires after 30 minutes and is capped at 500 staff entries;
  language hints are also bounded. Restarting clears only unfinished UI state.
- Domain errors remain server-logged. Only safe command-usage errors are shown directly; other
  failures return a localized generic message.
- Incremental infrastructure cost remains zero.
- The privacy notice was versioned to `2026-07-28-v2` because full name and preferred visit time
  are newly collected. Audit records do not duplicate name, phone, address, or description.

## 6. Known limitations

- Staff language override and unfinished guided flows are intentionally process-local for the
  single-instance pilot. Telegram client language supplies the restart fallback.
- Free text is still required when the business record genuinely needs a reason, description, note,
  result or summary.
- Configurable categories/checklists require an administrator to provide both Uzbek and Russian
  labels.
- CSV metric keys remain stable technical identifiers so exports are automation-safe; the Telegram
  report and document caption are localized.
- Preferred visit windows are not capacity reservations or resident-facing SLA promises; staff
  confirmation remains required for this near-zero-cost pilot.
